Projeto Silos — Documentação Técnica Geral

Plataforma IoT + IA para Monitoramento de Silos de Grãos

Sistema multi-tenant de telemetria, análise preditiva e controle remoto aplicado ao agronegócio brasileiro. Sensores embarcados em silos de soja transmitem dados via LoRa → gateway Labrador → nuvem, onde são processados por modelos de IA e exibidos em um portal web.

InfraestruturaDigitalOcean Droplet (157.245.139.143) Protocolo IoTMQTT 3.1.1 TLS (porta 8883) Banco de DadosPostgreSQL (schema silos + silos_ia) Modelo de IATCN — Temporal Convolutional Network Firmware ESP32LoRa, ciclos de 3 minutos Previsão48 horas à frente (horizonte)

Arquitetura do Ecossistema

O projeto é composto por quatro módulos de software que se comunicam entre si e com o hardware de campo. A topologia geral é:

  │  LoRa
  ▼

  │  MQTT TLS 8883 (Publisher)
  │  HTTP GET /v1/firmwares/{file} (OTA pull)
  ▼

  ├── PostgreSQL  ────────► linkmebr (portal web)
  ├── MQTT Subscriber/Publisher       │ HTTPS REST
  ├── /v1/labrador/comandos           ▼

                    HTTP
linkme-labrador-fake (simulador)
  └── Emula o Labrador real para testes

Os Quatro Módulos

linkmebr

Portal web React + Node.js. Dashboard com mapa Leaflet, relatórios, exportação CSV/JSON, esquemáticos, previsões de IA, comandos remotos, administração multi-tenant.

linkme-server

Servidor Python + FastAPI. Recebe telemetria MQTT do Labrador, persiste em PostgreSQL, expõe API REST para o portal e para o módulo de IA, roteia comandos remotos.

linkme-ia

Pipeline Python + TensorFlow. Treina modelo TCN com dados históricos, gera previsões de 48h para temperatura, umidade e CO2, sugere acionamento de aeradores.

linkme-labrador-fake

Simulador Python + React. Emula o gateway Labrador e os sensores físicos com modelos termodinâmicos realistas. Usado para desenvolvimento e validação offline.

Fluxo de Dados (Leitura de Sensor)

ESP32 acumula medições (3 min) → Pacote LoRa → Labrador → MQTT silos/<id>/leituras/<node> → linkme-server deserializa → PostgreSQL silos.leitura_interna → Portal / IA

Fluxo de Comando Remoto

Operador clica no portal → POST /v1/labrador/comandos → linkme-server assina HMAC → MQTT → Labrador → ESP32 executa → Resultado via MQTT → Portal exibe (polling 1–2s)

Hardware de Campo

Gateway Labrador

Dispositivo Linux ARM instalado fisicamente no silo. Responsável por receber pacotes LoRa dos DTGs e retransmitir via MQTT para o servidor na nuvem.

  • Arquitetura: Linux ARM (armhf), Docker Compose
  • Conectividade: Internet (MQTT TLS 8883) + rádio LoRa local
  • Autenticação MQTT: client_id = labrador-silo<N>, escopo ingest
  • Deduplicação de pacotes: hash SHA-256 do conteúdo JSON
  • Fallback REST: quando MQTT indisponível, usa endpoint HTTP alternativo

Protocolo de Acumulação (ESP32)

Cada ESP32 acumula leituras ao longo de um ciclo de 3 minutos e transmite estatísticas — nunca o valor bruto individual. O servidor reconstrói média e desvio padrão a partir dessas estatísticas.

Campo transmitidoDescriçãoEscala
sumΣ das leituras no ciclo×100 (temp/umid)
sum2Σ dos quadrados×100
valid_countNúmero de amostras válidas—
max / minExtremos do ciclo×100
tipo0=temp, 1=umid, 2=CO2—

Reconstrução server-side: avg = sum / valid_count / 100 (temp/umid) ou sum / valid_count (CO2).

Limitação conhecida — Desvio Padrão O ESP32 calcula o desvio padrão corretamente internamente (método TipoEstatistica::desvio(), em double precision), mas não o transmite. A reconstrução servidor-lado a partir de sum/sum2 sofre cancelamento catastrófico (~18% de erro). Recomendação: transmitir desvio() diretamente como campo extra (escala ×10000, uint16).

Firmware OTA

Modelo pull: o Labrador busca o binário autenticado via GET /v1/firmwares/{file_name} (escopo ingest). A resposta inclui o header X-Firmware-SHA256 para validação. Categorias: DTG01-04 e DTG05.

Comandos Remotos — Canal MQTT

O linkme-server assina cada comando com HMAC-SHA256 antes de publicar:

mensagem = f"{type}|{comando_id}|{parametro or ''}|{parametro_extra or ''}|{timestamp}|{nonce}"
signature = HMAC-SHA256(COMANDO_HMAC_SECRET, mensagem).hexdigest()

Payload publicado em silos/silo<N>/comandos:

{
  "type": "comando",
  "request_id": "f3a1c2e0-...",
  "comando_id": 4,
  "parametro": 104,
  "parametro_extra": null,
  "timestamp": 1700000000,
  "nonce": "a1b2c3d4",
  "signature": "9f8e7d..."
}

Resultado recebido do Labrador via MQTT:

{
  "type": "comando_resultado",
  "request_id": "f3a1c2e0-...",
  "comando_id": 4,
  "parametro": 104,
  "tipo": "lora",
  "status": "ok",
  "resultado": "ACK;104;REBOOT;OK",
  "returncode": null,
  "timestamp": 1700000002
}

O timeout_sweeper monitora comandos pendente e os marca como timeout automaticamente: 5s para sistema/banco, 15s para lora/OTA.

OTA de Firmware

Modelo pull: o Labrador autentica e busca o binário. O frontend só faz upload e lista — nunca baixa o .bin.

GET /v1/firmwares/{file_name}
Authorization: Bearer <token scope=ingest>
X-Firmware-SHA256: <hash para validação no Labrador>

Análise de Desvio Padrão — Limitação Conhecida

O ESP32 calcula o desvio padrão corretamente em double dentro do firmware (TipoEstatistica::desvio()), mas transmite apenas sum e sum2. A reconstrução servidor-lado produz erro de ~18% por cancelamento catastrófico.

Recomendação pendente: Incluir desvio() pré-calculado no payload (campo extra, escala ×10000, uint16). Mudança requer: atualização do parser no Labrador, atualização de db/sanitizer.py, e reprocessamento dos dados históricos.

linkme-ia — Pipeline de Inteligência Artificial

Treinamento e inferência de modelo TCN para previsão de 48h de condições no silo

Visão Geral

O linkme-ia é um serviço Python independente que consome dados do linkme-server via API REST (escopo export), treina um modelo de rede neural temporal (TCN) e publica previsões de 48h no banco silos_ia. A integração com o linkme-server é via MQTT e HTTP.

Arquitetura do Modelo TCN

CamadaDetalhe
Entrada480 timesteps × 36 features (24h de dados em ciclos de 3 min)
Blocos TCN6 blocos dilatados (dilation 1, 2, 4, 8, 16, 32)
Campo receptivo~500 pontos (~25h)
PoolingGlobalAveragePooling1D
DenseDense(512)
SaídaDense(960 × 36) → Reshape(960, 36) via UpSampling1D(2)
NormalizaçãoMinMaxScaler por sensor
ExportTFLite INT8 (~195 KB), Keras (~2–5 MB)

A saída são 960 timestamps (48h × 20 ciclos/hora), com 36 valores por timestamp (um por sensor monitorado), representando os valores previstos normalizados. O portal exibe esses valores após desnormalização.

Pipeline de Treinamento

Modos de Treino

ModoGatilhoDataset
bootstrapInterno — primeiro treinoTodo o histórico disponível
incrementalAutomático — diariamente 00:30 UTC90% últimas 24h + 10% histórico aleatório (anti-forgetting)
fullManual (admin via portal)Todo o histórico

Construção do Dataset

Abordagem em 2 passos: (1) contagem prévia para alocar tensores, (2) streaming com cache em disco. Split temporal 80%/20% (treino/validação, cronológico).

Sanitização de Dados

21 regras de sanitização divididas em 3 grupos. Exemplos: outliers físicos (temp > 60°C), gradientes impossíveis, sequências muito longas de valores constantes. Dados marcados com codes A1–A6, AH, E1–E6.

EarlyStopping

Monitoramento de val_loss, patience=10, restore_best_weights=True.

Armazenamento do Modelo

ArtefatoCampo DBTamanho aproximado
TFLite INT8tflite_bytes (BYTEA)~195 KB
Keras modelokeras_bytes (BYTEA)~2–5 MB
Scaler MinMaxscaler_bytes (BYTEA)<5 KB

Inferência

Executada diariamente às 01:00 UTC. Lê as últimas 480 leituras (24h) do silo, executa um forward pass no modelo TFLite, gera 960 previsões.

Controle de Aeração

O pipeline compara leituras reais vs. previsões e sugere acionamento de aeradores quando os desvios excedem os limites:

VariávelLimiar de desvio
Temperatura≥ 2°C
Umidade relativa≥ 5%
CO2≥ 200 ppm

Sugestão publicada no tópico aerador/{silo_id}/evento. O acionamento efetivo do relé (DTG05) é feito via comando remoto comando_id=5/6.

linkme-labrador-fake — Simulador

Emulador do gateway Labrador com modelos físicos de silo de soja para testes e desenvolvimento

O simulador gera dados sintéticos realistas de um silo de soja, publica via MQTT (mesmo protocolo do Labrador real) e salva em silos.dados_simulados (tabela separada dos dados reais). Roda em Docker sobre armhf (compatível com o Labrador físico).

Sensores Simulados

40 sensores no total:

  • 4 cabos internos × 3 alturas × 3 tipos (Temperatura / Umidade / CO2) = 36 sensores internos
  • 1 cabo externo × 4 tipos (Temperatura / Umidade / CO2 / Relé) = 4 sensores externos

Modelo físico do silo: 180 kg de soja, 1150 mm de altura total (600 mm cilindro + 350 mm cone), 600 mm de diâmetro.

RespiraçãoQ10 (coeficiente de temperatura)Base = 0.5 mg CO2/kgMS/dia

Perfis climáticos externos: Sorriso/MT, 12 meses (Köppen Aw), com variação diária e sazonal.

Volume Estimado

Referência: 1 empresa × 5 silos × 2 barras × 3 sensores = 30 sensores → ~480 leituras/dia/sensor → ~144.000 registros/dia na leitura_interna.

Firmware armazenado como BYTEA — Os binários .bin são armazenados diretamente na tabela firmwares como BYTEA (PostgreSQL). Não há sistema de arquivos externo para os firmwares.

Cliente MicroPython (ESP32C)

Restrições MicroPython: O cliente embarcado usa umqtt.robust, ujson, utime, ntptime. Sem datetime, logging, ou threading. Conexão MQTT: TCP puro, porta 1883 (sem TLS para este cliente específico, user: silo2_mqtt). O acumulador de temperatura/umidade usa escala ×100 igual ao firmware Arduino.

Segurança

Autenticação JWT

Algoritmo HS256. Múltiplos escopos com permissões distintas:

EscopoQuem usaPermissões
adminPortal (admins)Disparar comandos, upload de firmware, gestão completa
readPortal (operadores e admins)Consulta de dados, histórico, previsões
ingestLabradorPublicação de telemetria, download de firmware OTA
exportlinkme-iaExportação de leituras para treino

Proteções do Portal (linkmebr)

  • JWT: Expiração em 8h (padrão); blacklist via Redis no logout
  • Senhas: bcrypt
  • Headers HTTP: Helmet.js
  • Rate limiting login: 5 tentativas por 15 minutos por IP
  • Rate limiting contato: 3 requisições por hora
  • Multi-tenancy: Isolamento por empresa em todas as queries

Segurança de Comandos Remotos

  • Cada comando é assinado com HMAC-SHA256 usando COMANDO_HMAC_SECRET
  • O Labrador verifica a assinatura antes de executar
  • Campos incluídos na assinatura: type, comando_id, parametro, parametro_extra, timestamp, nonce
  • Replay attacks mitigados via timestamp + nonce

Transporte

  • MQTT: TLS na porta 8883 para todos os clientes de produção
  • HTTP: HTTPS via nginx (terminação TLS)
  • Exceção: ESP32C com MicroPython usa porta 1883 TCP (sem TLS) por limitação de memória do dispositivo

OTA de Firmware

  • Firmware autenticado (escopo ingest) antes do download
  • Hash SHA-256 enviado no header X-Firmware-SHA256 para validação no Labrador
  • Upload restrito a usuários com escopo admin

Multi-tenancy

Hierarquia de isolamento: empresa → usuários → silos → barras → sensores. Nenhum dado de uma empresa é acessível por usuários de outra empresa, mesmo no mesmo banco. Validação enforçada em todas as queries do backend.
